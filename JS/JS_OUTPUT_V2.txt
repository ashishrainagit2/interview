Q3. let x = 0.1 + 0.2;
let y = 0.3;
console.log(x == y);

Ans. false
Why does this happen?
Computers store decimals in binary, and some decimal numbers (like 0.1 and 0.2) cannot be represented exactly. Small rounding errors add up, so 0.1 + 0.2 is not exactly 0.3.

1. Humans use base 10, computers use base 2
We use base 10: digits 0–9, and each place is a power of 10.
123.45 = 1×10² + 2×10¹ + 3×10⁰ + 4×10⁻¹ + 5×10⁻²
Computers use base 2 (binary): only 0 and 1, each place is a power of 2.
101.1₂ = 1×2² + 0×2¹ + 1×2⁰ + 1×2⁻¹ = 4 + 0 + 1 + 0.5 = 5.5

2. Some decimals have no exact binary form
In base 10, 1/3 = 0.333333… — it never ends.
In base 2, 0.1 and 0.2 behave the same way: they never end.
0.1 in binary:
2⁻¹	2⁻²	2⁻³	2⁻⁴	2⁻⁵	2⁻⁶	...
0.5	0.25	0.125	0.0625	0.03125	0.015625	...
To get 0.1, you need combinations of these powers of 2. The result is an infinite repeating pattern:

0.1₁₀ = 0.0001100110011001100110011...₂  (repeats forever)

0.2 in binary is just 0.1 shifted one place:
0.2₁₀ = 0.001100110011001100110011...₂  (repeats forever)
So there is no finite binary representation for 0.1 or 0.2.

3. Computers must round to fit
A number like 0.1 is stored in a fixed number of bits (e.g. 64 bits in IEEE 754 double-precision). The infinite binary expansion must be cut off and rounded.
Example:
0.1 is stored as:
0.1000000000000000055511151231257827021181583404541015625
0.2 is stored as:
0.200000000000000011102230246251565404236316680908203125
These are the closest values the computer can represent in 64 bits.

4. Adding them introduces more error
When you add these rounded values:
  ~0.10000000000000000555111512312578...+ ~0.20000000000000001110223024625156...─────────────────────────────────────────= ~0.30000000000000004440892098500626...
So 0.1 + 0.2 in JavaScript is stored as something like 0.30000000000000004, not exactly 0.3.

5. Why 0.3 looks “exact” but 0.1 + 0.2 doesn’t
When you write 0.3, the computer stores the closest representable value to 0.3, which is slightly different from the result of adding the stored 0.1 and 0.2. So:
0.3 → stored as one specific approximation
0.1 + 0.2 → stored as another approximation (from two rounded values plus rounding of the sum)
Those two approximations are not identical, so 0.1 + 0.2 === 0.3 is false.

Step	What happens
1	0.1 and 0.2 have infinite binary expansions
2	The computer rounds them to fit in 64 bits
3	Adding these rounded values introduces more rounding
4	The sum is not exactly 0.3, so 0.1 + 0.2 === 0.3 is false
This is a limitation of binary floating-point, not of JavaScript. Most programming languages that use IEEE 754 floating-point behave the same way.

Any language that uses IEEE 754 float/double will show this behavior. It comes from how hardware represents decimals, not from the language itself

In the first comparison (x == y), x is a Boolean (false) and y is a string ("0"). Since both false and "0" can be coerced to the Boolean false, the comparison returns true.

Q23. const a = { b: { c: 2 } };

Explanation:
This happens because the spread operator { ...a } makes a shallow copy, not a deep copy.
What happens
a = { b: { c: 2 } }
a.b points to the object { c: 2 }.
b = { ...a }
Top-level properties are copied.
a.b is an object, so its reference is copied, not a clone.
So b.b and a.b both refer to the same object.
a.b.c = 3
Mutates the shared object { c: 2 } to { c: 3 }.
console.log(b.b.c)
b.b still points to the same object, so b.b.c is now 3.
Visual
Before a.b.c = 3:   a ──► { b: ──► { c: 2 } }   b ──► { b: ──► same object }After a.b.c = 3:   a ──► { b: ──► { c: 3 } }  ◄── shared object   b ──► { b: ──► same object }
Shallow vs deep copy
Copy type	What gets copied	Result
Shallow { ...a }	Top-level values only	Nested objects are shared
Deep	All levels cloned	Nested objects are independent
How to deep copy
const b = JSON.parse(JSON.stringify(a));  // Simple (no functions, dates, etc.)// orconst b = structuredClone(a);  // Modern approach (no functions)
With a deep copy, a.b.c = 3 would not change b.b.c, and b.b.c would still be 2.

Q26. let x = [1, 2, 3];
let y = x.map((num) => {
  x.push(num + 3);
  return num + 1;
});

console.log(y);

Ans. [2, 3, 4]

Explanation: In this code, an array x is initially defined with the elements [1, 2, 3]. The .map() function is then called on x, iterating over each element and applying the provided callback function. The callback function takes num (the current element), returns num + 1, and simultaneously pushes num + 3 to the array x. However, an important aspect of .map() is that it determines the number of iterations based on the array's initial length before modifications occur. Since x originally contains three elements, .map() will only execute for the first three elements (1, 2, 3), even though new elements (4, 5, 6) are being pushed to x during the iteration.

This means that map() does not dynamically process the newly added elements, and it strictly iterates three times. As a result, the new array y is created by mapping [1, 2, 3] to [2, 3, 4], while x is mutated to [1, 2, 3, 4, 5, 6] by the end of the execution. This behavior occurs because .map() is not influenced by modifications made to the array after iteration begins. Thus, when console.log(y) is executed, the output is [2, 3, 4], while console.log(x) outputs [1, 2, 3, 4, 5, 6]
