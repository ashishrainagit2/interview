Q2. var num = 10; 
(()=>{ 
   console.log(num) 
   var num = 20; 
   console.log(num) 
})() 

Ans. This snippet shows how hoisting and variable shadowing work in JavaScript.

OUTPUT: 
undefined
20

WHY?

Hoisting
var declarations are hoisted to the top of their scope. Inside the IIFE, the engine effectively treats it like:
   (()=>{ 
      var num;        // hoisted, value is undefined
      console.log(num)  // undefined
      num = 20; 
      console.log(num)  // 20
   })() 
Shadowing
The inner var num creates a local variable that shadows the outer num = 10. Inside the IIFE, num always refers to the local one, not the global.
First console.log(num)
At this point, the local num exists (because of hoisting) but hasn’t been assigned yet, so it’s undefined. The outer num = 10 is not used because of shadowing.
Second console.log(num)
After num = 20, the local num is 20, so it logs 20.

Q3. console.log( this) 
    let obj = { 
        name: "Name", 
        thisObj: this, 
        someFunction:function(){ 
            return this; 
        }, 
        someArrowFunction: () => { 
            return this; 
        } 
    } 
console.log(obj.thisObj) 
console.log(obj.someFunction()) 
console.log(obj.someArrowFunction())


ANS.
Explanation
1. console.log(this) (first)
Runs in the global scope. In a browser it logs window; in Node it logs global.
2. thisObj: this
thisObj is set when the object is created. At that moment the code is still in the global scope, so this is the global object. That value is stored in thisObj and never changes.
3. obj.someFunction()
Regular function called as a method. In that case, this is the object the method is called on, i.e. obj. So it returns the obj object.
4. obj.someArrowFunction()
Arrow functions don’t have their own this; they use this from the surrounding scope. Object literals {} do not create a new scope, so the arrow function’s this comes from the global scope (or wherever this code runs), not from obj. So it returns the global object again.
Summary
Expression	this refers to
this (global)	Global object
thisObj: this	Global object (captured at creation)
obj.someFunction()	obj (caller)
obj.someArrowFunction()	Global object (lexical scope)
Takeaway: Arrow functions inherit this from where they are defined, not from how they are called.

OUTPUT:

Window 
Window
{name: 'Name', thisObj: Window, someFunction: ƒ, someArrowFunction: ƒ}

Q4.
   console.log("one")  
   setTimeout(()=>{console.log("after 1 sec")},1000)  
   setTimeout(()=>{console.log("after 0 sec")},0)  
   const promise = new Promise(resolve=>{ 
      console.log("three");  
      resolve("four") 
   } 
   )  
   promise.then(data=>console.log(data))  
   console.log("two")  
   setTimeout(()=>{console.log("after 000 sec")},0)  
   setTimeout(()=>{console.log("after 00 sec")}) 

Ans.
OUTPUT:
one
three
two
four
85
after 0 sec
after 000 sec
after 00 sec
after 1 sec

Step-by-step
Phase 1: Synchronous execution
console.log("one") → logs "one"
setTimeout(..., 1000) → schedules callback in ~1 second
setTimeout(..., 0) → schedules callback for next event loop tick
new Promise(...) → executor runs immediately:
console.log("three") → logs "three"
resolve("four") → promise resolves
promise.then(...) → adds callback to microtask queue
console.log("two") → logs "two"
setTimeout(..., 0) → schedules another callback
setTimeout(...) (no delay) → same as setTimeout(..., 0)
Phase 2: Microtasks (before next macrotask)
Microtask queue runs before the next macrotask.
promise.then callback runs → logs "four"
Phase 3: Macrotasks (timer callbacks)
setTimeout callbacks run in the order they were scheduled:
"after 0 sec"
"after 000 sec"
"after 00 sec"
Phase 4: After ~1 second
"after 1 sec" runs
Concepts
Concept	Behavior
Synchronous code	Runs first: "one", "three", "two"
Promise executor	Runs immediately when the promise is created
Microtasks	Run before the next macrotask; promise.then runs before setTimeout callbacks
Macrotasks	setTimeout callbacks run in order after microtasks
setTimeout(fn)	Same as setTimeout(fn, 0)
Takeaway: Microtasks (promises, queueMicrotask) run before macrotasks (setTimeout, setInterval, I/O).

Q5. function createTimers() { 
    for (var i = 1; i <= 5; i++) { 
        setTimeout(function() { 
            console.log(i); 
        }, 1000); 
    } 
} 

OUTPUT: 
6
6
6
6
6

Why?
var is function-scoped
There is a single i for the whole function, not one per loop iteration.
Closures capture the variable, not the value
Each setTimeout callback closes over the same i.
Timing
When the callbacks run (after 1 second), the loop has already finished. At that point i is 6 (the value that made i <= 5 false and ended the loop).
Result
All 5 callbacks log the same i, which is 6.

Fix: use let
function createTimers() { 
    for (let i = 1; i <= 5; i++) { 
        setTimeout(function() { 
            console.log(i); 
        }, 1000); 
    } 
} 
This logs 1, 2, 3, 4, 5 because let creates a new binding per iteration, so each callback captures its own i.

1. IIFE (Immediately Invoked Function Expression)
Create a new scope per iteration so each callback gets its own i:
function createTimers() { 
    for (var i = 1; i <= 5; i++) { 
        (function(j) {
            setTimeout(function() { 
                console.log(j); 
            }, 1000); 
        })(i);
    } 
}

Each iteration runs (function(j) { ... })(i).
i is passed in as j.
Each IIFE has its own j in its scope.
Each callback closes over its own j, not the shared i.
So you get 1, 2, 3, 4, 5.

2. Pass i as an argument to 
function createTimers() { 
    for (var i = 1; i <= 5; i++) { 
        setTimeout(function(j) { 
            return function() { console.log(j); };
        }(i), 1000); 
    } 
}

3. Use bind

function createTimers() { 
    for (var i = 1; i <= 5; i++) { 
        setTimeout(function(j) { 
            console.log(j); 
        }.bind(null, i), 1000); 
    } 
}

4. Use forEach (creates a new scope per iteration)
function createTimers() { 
    [1, 2, 3, 4, 5].forEach(function(i) { 
        setTimeout(function() { 
            console.log(i); 
        }, 1000); 
    }); 
}

Summary
Solution	Idea
let	    Block-scoped binding per iteration
IIFE	New function scope per iteration
bind	Pre-fill argument for the callback
forEach	Callback gets its own parameter per iteration
In modern code, let is usually the simplest and clearest option.

Q6. Explain the output of the following code:

function getPromise() {
    return new Promise(function(resolve, reject) {
        resolve();
    })
}

let promise = getPromise()

promise
.then(() => console.log("Success 1"))
.then(() => console.log("Success 2"))
.then(() => console.log("Success 3"))
.catch(() => console.log("Error"))
.then(() => console.log("Success 4"))

Explanation
getPromise() returns a Promise that resolves immediately (no value).
.then() chain
Each .then() runs in order because the previous step resolves successfully:
First .then() → logs "Success 1"
Second .then() → logs "Success 2"
Third .then() → logs "Success 3"
.catch()
No error occurs, so .catch() is never called and does not log anything.
.then(() => console.log("Success 4"))
Because the chain never rejects, this .then() still runs and logs "Success 4".
Takeaway: .catch() only runs when there is a rejection. If all steps resolve, the .then() after .catch() still executes.

Q7. What will be the output of this code?

console.log(1 < 2 < 3);
console.log(3 > 2 > 1);

true
false

Why does this happen?
Because JavaScript evaluates expressions step by step.

1 < 2  → true
true < 3 → 1 < 3 → true

But in the second case:

3 > 2  → true
true > 1 → 1 > 1 → false

JavaScript silently converts true into 1.
No error.
No warning.
Just unexpected behavior.
This is why understanding type coercion in JavaScript is so important.
Sometimes the bug isn't in the code…
It's in our assumptions about how JavaScript works.

Q8. What will be the output of this code?

console.log('1');
setTimeout(() => {
   console.log('2');
}, 0);
Promise.resolve(console.log('3'));
console.log('4');

// 1 , 3, 4, 2

Promise.resolve(...) does not delay whatever you put inside the parentheses.

The rule: arguments are evaluated before the function runs. So this happens in order, on the main thread, right away:

console.log('3') is called immediately (that’s why you see 3 printed now).
console.log returns undefined.
Promise.resolve(undefined) runs and creates an already-resolved promise (also synchronous).
So the logging is synchronous because it’s not “inside” the promise’s async work — it’s inside the argument list, which must be computed before Promise.resolve is invoked.

If you want 3 to print later (after current sync code, in a microtask), do:

Promise.resolve().then(() => console.log('3'));
There, only the callback runs asynchronously; the console.log is deferred until the .then runs.
